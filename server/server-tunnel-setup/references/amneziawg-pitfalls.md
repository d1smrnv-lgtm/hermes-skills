# AmneziaWG / WireGuard — частые ошибки и фиксы

## Бинарник `awg` ≠ `awk`: молчаливая подмена команды

На Ubuntu/Debian с установленным `amneziawg-tools` команда `awg` может совпасть с именем встроенного инструмента или алиасом, из-за чего `awg show awg0 dump` превращается в ошибку awk и выводит что-то вроде:

```
awk: fatal: cannot open file 'awg0' for reading
```

**Как проверять:**
- Запускать через полный путь: `/usr/bin/awg show <iface> dump`
- Или проверить, куда указывает бинарник: `which awg && ls -l $(which awg)`
- Если там не `/usr/bin/awg` — использовать абсолютный путь везде

**Почему это важно:** Ошибка выглядит как проблема с конфигурацией туннеля, хотя на самом деле команда вообще не выполнилась.

## Переключение между стандартным WireGuard (`wg`) и AmneziaWG (`awg`)

Два набора инструментов共存на одной машине: `wireguard-tools` (`wg` + `wg-quick`) и `amneziawg-tools` (`awg` + `awg-quick`). Они создают разные интерфейсы (`wg0` vs `awg0`) и **не удаляют друг друга при рестарте**.

Если нужно заменить туннель с одного типа на другой:

1. **Остановить обе службы:**
   ```bash
   systemctl stop wg-quick@wg0.service
   systemctl stop awg-quick@awg0.service
   ```

2. **Удалить старый интерфейс ядра вручную:**
   ```bash
   ip link del <old_iface>  # eg. ip link del awg0
   ```

3. **Ждать завершения cleanup:** `sleep 2`

4. **Только тогда создавать новый интерфейс и запускать службу.**

Без шага 2 новый `ip link add <iface>` часто падает с «device already exists».

## Конфиг-файл ≠ реальная конфигурация AmneziaWG

AmneziaWG installer сохраняет параметры в память и **перезаписывает `/etc/wireguard/awg0.conf` при каждом `systemctl restart`**, игнорируя ваши изменения.

**Правильный workflow для смены настроек:**
- Генерировать ключи: `awg genkey > private`, `awg pubkey < private > public`
- Применять настройки через `awg setconf <iface> /path/to/conf` (сначала создать интерфейс: `ip link add <iface> type amneziawg`)
- Либо применять через `awg set <iface> ...` после запуска службы
- Валидировать через `awg show <iface> dump` — только он показывает реальное состояние
- Файл `/etc/wireguard/awg0.conf` использовать как источник правды для следующего запуска, но не полагаться что он сохранится автоматически

## Проблема с NAT при нескольких подсетях

При наличии двух туннелей (awg0 subnet + wg0 subnet) широкое правило MASQUERADE без источника:

```iptables
-A POSTROUTING -o eth0 -j MASQUERADE
```

может перехватывать трафик от обоих туннелей, но без учёта приоритетов правила. 

**Решение:** Явно указывать исходную подсеть:
```iptables
-A POSTROUTING -s 192.168.255.0/24 -o eth0 -j MASQUERADE
-A POSTROUTING -s 10.9.9.0/24 -o eth0 -j MASQUERADE
```

## Успешные клиенты при битых пакетах

Иногда handshake есть (`PersistentKeepalive: every 25 seconds`), пакеты идут в оба направления, но интернет не работает:

Проверьте:
- FORWARD для исходящего трафика: `-A FORWARD -o <tunnel_iface> -m state --state RELATED,ESTABLISHED -j ACCEPT`
- NAT: маскарадинг должен охватывать клиентскую подсеть
- MTU: туннельные интерфейсы обычно имеют MTU 1280–1420; если у клиента меньше — TCP фрагментируется
- DNS: если у клиента DNS настроен только на внутренний сервер, а он недоступен — сайты не грузятся. Используйте публичные DNS (8.8.8.8, 1.1.1.1).

## Диалект конфига должен совпадать с мобильным приложением

Клиентские приложения строго разделяют два диалекта конфигурации:

| Приложение | Принимает | Отклоняет |
|---|---|---|
| AmneziaWG (иконка A) | AWG: [Interface] c Jc/Jmin/Jmax/S1/S2/H1-H4 | чистый WG-конфиг без этих параметров |
| WireGuard (официальное) | чистый WG: PrivateKey/Address/DNS + Peer | любой параметр AWG с ошибкой unknown section in config |

Порядок действий: до генерации конфига уточнить приложение. Если клиент репортит «unknown section in config» — это несовпадение диалекта с приложением, а не битый файл и не битый QR; перегенерация того же диалекта ошибку не лечит. Быстрый путь при неопределённости: поднять на сервере ОБА туннеля параллельно (awg0 + wg0, разные подсети, MASQUERADE отдельно по каждой подсети) и выдать два конфига — какой примет приложение, тот рабочий.

## QR для мобильных клиентов: payload config=

Приложения сканируют не сырой текст конфига, а строку `config=` + URL-encoded весь .conf:

```bash
PAYLOAD=$(python3 -c "import urllib.parse; print('config='+urllib.parse.quote(open('/etc/wireguard/client.conf').read().strip(), safe=''))")
/usr/bin/qrencode -o /tmp/qr.png -s 8 -m 4 "$PAYLOAD"
```

- qrencode с `-r file.conf` кодирует сырой текст — приложение не распознаёт его как туннель.
- `-m 4` (quiet zone) обязателен: без белой рамки сканер не находит границы кода.
- `-s 8` и выше: при мелком модуле код полного конфига (~340 байт) не читается с экрана.
- Готовый PNG показывать через MEDIA:, ANSI-версия в терминал для телефона бесполезна.
